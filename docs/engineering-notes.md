# 엔지니어링 노트 — 구현 중 마주친 문제와 해결

> RAG 챗봇을 만들며 실제로 부딪힌 문제들의 **증상 → 원인 → 해결 → 교훈** 기록.
> 라이브러리를 붙였다가 아니라, 재보고 판단한 과정을 남긴다.

---

## 1. 신형 LLM API 대응 — 응답이 문자열이 아니었다

**증상**: Gemini 연결 후 답변이 `[{'type': 'text', 'text': '...'}, {'extras': {...}}]` 처럼 깨져 출력됨.

**원인**: Gemini 3.x 계열은 응답 `content` 를 문자열이 아니라 **파트 배열**로 반환한다.
기존 코드가 `isinstance(content, str)` 가 아니면 `str(content)` 로 떨어뜨려, 리스트를 통째로 문자열화하고 있었다.

**해결**: text 파트만 골라 이어붙이는 정규화 함수(`_text_of`)를 도입. thinking·서명 등 비텍스트 파트는 버린다.

**교훈**: 최신 모델은 멀티파트 응답이 기본이 되어간다. content 를 문자열로 가정하지 말 것. (`app/rag.py`)

## 2. 모델이 "사라졌다" — 404 no longer available

**증상**: `gemini-2.5-flash` 호출 시 404 NOT_FOUND, "no longer available to **new users**".

**원인**: 기존 사용자에겐 남아 있어 문서엔 보이지만, 신규 발급 키에는 제공되지 않는 모델이었다.

**해결**: API 로 실제 사용 가능한 모델을 나열 → 후보를 직접 호출해 통과하는 것만 채택.
품질·지연을 재서 `gemini-3.1-flash-lite` 선택(첫 토큰 1.4s, 3.5-flash 는 thinking 탓 ~20s).

**교훈**: 모델 가용성은 키/계정마다 다르다. 문서보다 런타임 probe 가 진실.

## 3. 첫 질문만 18.6초 — LLM 이 아니라 임베딩이 범인

**증상**: 서버 기동 후 첫 질문이 18.6초, 이후는 1~2초.

**원인**: 지연 로딩. 첫 검색 때 HuggingFace 임베딩 모델을 처음 적재하는 비용이었다(LLM 아님).

**해결**: FastAPI `lifespan` 에서 기동 시 검색을 1회 미리 실행(워밍업) → 첫 질문 3.5초.

**교훈**: 체감 지연을 LLM 탓으로 넘겨짚지 말고 구간을 나눠 측정. 콜드스타트는 워밍업으로 옮긴다.

## 4. 재인덱싱이 계속 실패 — 좀비 프로세스의 파일 잠금

**증상**: `ingest --reset` 이 `PermissionError [WinError 32]` (다른 프로세스가 chroma_db 사용 중).

**원인**: 이전 세션에서 죽인 uvicorn 의 **고아 자식 프로세스**(멀티프로세싱 워커)가 포트와
Chroma 파일을 계속 물고 있었다. 부모만 죽였지 자식이 남았다.

**해결**: `Get-CimInstance Win32_Process` 로 명령줄까지 확인해 이 프로젝트 소속 프로세스만 정리.
(같은 머신의 다른 실서비스 프로세스는 건드리지 않도록 CommandLine 으로 식별)

**교훈**: Windows 에서 프로세스 트리를 죽일 때 자식이 남을 수 있다. 포트/파일 잠금은 PID 가 아니라 명령줄로 추적.

## 5. 하이브리드 검색의 함정 — MMR 이 하이브리드를 무효화

**증상**: BM25+벡터를 RRF 로 융합했는데, "ERR7742 오류" 같은 **희귀 식별자** 질문에서
정작 그 식별자를 담은 문서가 최종 top-k 에서 탈락.

**원인**: 중복 제거용 MMR 의 적합도 항에 **코사인 유사도**를 쓰고 있었다. BM25 가 순위를 올려준
문서라도 코사인이 낮으면 MMR 재선택에서 밀려, 하이브리드로 얻은 이점이 마지막에 사라졌다.

**해결**: MMR 적합도 항을 **RRF 융합 점수**로 교체. 임베딩은 중복 penalty 계산에만 사용.

**교훈**: 파이프라인 마지막 단계가 앞 단계의 신호를 흘리면 앞의 노력이 무의미해진다. 신호를 끝까지 보존하라.

## 6. 범위 밖 질문 걸러내기 — BM25 는 게이트로 못 쓴다

**증상**: "고양이 키우는 법" 같은 잡담을 어휘 점수로 거르려 했더니 BM25 가 16점(높음)을 줌.

**원인**: 형태소 분석기 없이 한글을 2-gram 으로 토큰화하다 보니, 흔한 음절이 코퍼스 곳곳과
겹쳐 무관한 질문도 높은 BM25 를 받았다. (범위 안 0.40~0.72 / 밖 0.25~0.29 는 **코사인** 기준)

**해결**: 범위 밖 게이트는 **코사인 유사도 단독**(임계 0.35)으로. BM25 는 순위 매기기에만 쓰고
게이트에선 배제. 실측 분포로 임계 보정.

**교훈**: 지표를 쓰기 전에 그 지표의 분포를 그려보라. "높으면 관련"이 항상 참은 아니다.

## 7. 리랭커 — SOTA 라고 무지성으로 넣지 않는다

**증상**: cross-encoder 리랭커를 얹었더니 **코드 질문 recall 이 75%→50% 로 하락**.

**원인**: (1) 경량 모델(bge-reranker-base)은 코드 청크에 ~0점을 줘 자연어 문서를 선호,
RRF 가 완벽히 뽑은 `worker_main.py` 를 문서로 뒤집었다. (2) 대형 모델(v2-m3)은 분별력은
낫지만 "…코드에서?" 질문도 문서를 1위로 올리고 CPU 4.4초/질문. cross-encoder 가
자연어↔자연어 매칭을 자연어↔코드보다 선호해 "코드" 의도를 잃는 게 근본 원인.

**해결**: 두 모델을 평가셋으로 측정 → **기본 비활성화**. 구현·토글은 남겨 실험 가능하게.

**교훈**: 유명 기법이 항상 이득은 아니다. 넣기 전·후를 같은 평가셋으로 재고 근거로 판단.

## 8. 평가가 타임아웃 — 질문마다 모델을 새로 로드하고 있었다

**증상**: 검색 평가가 "Loading weights" 를 반복하며 10분 초과.

**원인**: `get_embeddings()` 에 캐시가 없어, 매 질문의 `embed_query` 마다 HuggingFace 모델을
디스크에서 다시 적재하고 있었다.

**해결**: `lru_cache(maxsize=1)`. 벡터스토어 코퍼스도 이미 캐싱돼 있었으나 임베딩 함수만 누락돼 있었다.

**교훈**: 무거운 리소스는 팩토리에 캐시를 건다. "느리다"의 원인은 대개 반복 초기화.

## 9. 코드를 검색 가능하게 — 한국어 질문 ↔ 영어 코드

**증상**: "apply_retry_policy 함수 코드 보여줘" 라고 물어도 함수 본문이 검색 top-5 에 안 옴.
답변은 "코드가 포함되어 있지 않다"고 함.

**원인**: 코드 청크는 영어 식별자뿐이라 한국어 질문과 임베딩 유사도가 낮다. 함수를 *언급한*
한국어 문서가 함수 *본문* 보다 상위에 왔다.

**해결**: **심볼 정확 매칭**. 질문에 코드 심볼명(`apply_retry_policy`)이 그대로 있으면 그 청크를
top-k 에 최대 2개 보장. 나머지 슬롯은 일반 검색 유지(→ "batch_deadline 시각?"처럼 정답이 문서인
질문을 코드가 독점하지 않게).

**교훈**: 임베딩이 약한 지점(언어·양식 불일치)은 정확 매칭 규칙으로 보완. 단, 강제 삽입은
개수를 제한해 다른 질문을 해치지 않게 한다.

## 10. AST 청킹 — 코드는 함수 단위로 잘라야 한다

**증상(예방)**: 고정 길이로 코드를 자르면 함수가 허리에서 잘려 "무엇을 하는지" 알 수 없는 조각이 생긴다.

**해결**: `ast` 로 파싱해 top-level 함수·클래스(큰 클래스는 메서드) 단위로 분할.
각 청크 앞에 `# 파일: … / # 심볼: …` **컨텍스트 헤더**를 붙여, 코드 조각만 임베딩해도
위치 정보를 잃지 않게 함(Contextual Retrieval 의 LLM 없는 경량판).

**교훈**: 청킹은 데이터의 의미 단위를 따라야 한다. 코드의 의미 단위는 줄 수가 아니라 함수다.

## 11. 문서와 코드가 어긋날 때 — 무엇을 진실로?

**상황**: `RATE_CAP` 이 문서엔 남아 있으나 코드에선 제거됨(설정 체계 개편 때).

**해결**: 프롬프트에 "문서와 코드가 어긋나면 명시하고, **실제 동작은 코드를 기준**으로" 지시.
지식원에 코드·git 이력을 함께 넣었기에 가능한 판단.

**교훈**: 다중 소스 RAG 는 소스 간 신뢰 우선순위를 정해야 한다. 실행 진실은 코드에 있다.

## 12. 무료 티어 레이트리밋 — 429 를 설계에 반영

**증상**: LLM-as-judge 평가가 분당 15요청 제한(무료 티어)에 걸려 429 로 크래시.

**해결**: 요청 간 선제 throttle + 429 응답의 `retryDelay` 를 파싱해 대기 후 재시도.

**교훈**: 무료/제한 API 는 레이트리밋이 정상 경로다. 예외가 아니라 흐름 제어로 다룬다.

## 13. 코퍼스가 커지면 최적값도 바뀐다 — MMR λ 재측정

**증상**: 문서만일 때 최적이던 MMR `λ=0.8` 이, 코드+git(3619청크) 확장 후 recall 을 깎음.

**원인**: 코퍼스가 커지자 유사 청크가 많아져, MMR 다양성이 정답을 밀어내는 부작용이 이득을 넘었다.

**해결**: git 인덱싱 후 λ 재스윕(0.9→86% / 0.95→89% / 1.0→93%) → 다양성 off(`λ=1.0`) 채택.

**교훈**: 하이퍼파라미터는 데이터에 종속된다. 코퍼스가 바뀌면 재측정. (지표를 CI 로 지키면 이런 회귀를 조기에 잡는다 — 향후 과제)

## 14. LLM 심사관도 공정한 입력을 줘야 — self-judge 편향

**증상**: 답변 groundedness 평가에서 judge 가 "이 파일명은 근거에 없다"며 정상 답변을 감점.

**원인**: judge 에게 준 근거에 파일명 헤더를 빼고 본문만 줬다. 생성기는 파일명을 봤는데 심사관은 못 봤다.

**해결**: 생성기와 **동일한 근거 포맷**(`_format_context`)을 judge 에도 제공. 프로젝트명 등 메타
표현은 감점 대상에서 제외.

**교훈**: LLM 평가의 신뢰도는 입력 공정성에서 온다. 생성기와 심사관의 정보 격차를 없애라.

## 15. 브루트포스 전수매칭은 "그렇게 된 것"이 아니라 고른 것 — ANN 전환 임계를 재다

**증상**: 없다. 이 항목은 버그가 아니라 **설명되지 않은 설계**였다.

`app/retriever.py` 의 `_corpus()` 는 Chroma 에서 청크·임베딩을 **전부 꺼내 프로세스 메모리에 올리고**,
검색은 numpy 행렬곱(코사인)과 `BM25Okapi` 전수 채점으로 한다.
즉 **Chroma 의 ANN 인덱스는 질의에 관여하지 않고, 사실상 디스크 blob 저장소로 쓰인다.**
"벡터 DB 를 썼다"는 말과 실제 동작이 어긋나는 지점이라, 물으면 답이 궁해지는 자리였다.

**측정**(실측 코퍼스 N=3,619 · 768dim, 로컬 CPU):

| N | 벡터 전수매칭 | 임베딩 행렬 |
|---:|---:|---:|
| 3,619 (현재) | **0.12 ms** | 11 MB |
| 10,000 | 0.3 ms | 31 MB |
| 100,000 | 5.1 ms | 307 MB |
| 500,000 | 27.5 ms | 1,536 MB |

같은 조건에서 **BM25 전수 채점은 4.7 ms** — 벡터 전수매칭보다 **40배 느리다**.
그리고 답변 첫 토큰까지는 약 1,400 ms 다.

**해석**: 현재 규모에서 exact 검색은 전체 지연의 **0.01%** 다. 여기에 ANN 을 얹으면
근사 오차만 떠안고 얻는 게 없다(exact 는 정의상 recall 상한이다). 최적화가 필요했다면
대상은 벡터가 아니라 BM25 였다 — **어림짐작이었으면 반대편을 팠을 것이다.**

**전환 임계**: 지연으로는 N=100,000 에서도 5 ms 라 문제가 안 된다. 먼저 무너지는 건 **메모리**다.
코퍼스 전체를 프로세스에 상주시키므로 **인스턴스 사양과 콜드스타트가 데이터 크기에 비례**한다.
Fargate 1 GB 구성 기준으로 임베딩 행렬 300 MB(N≈10만)가 임베딩 모델·런타임과 함께 올라갈 수 있는 한계다.
→ **N ≈ 10만이 ANN(또는 pgvector 서버사이드 검색) 전환 임계**이고, 그 전까지는 exact 가 더 정확하고 더 빠르다.

**교훈**: 리랭커를 측정해서 껐던 것과 같은 종류의 판단인데, 이건 기록이 없어서 **판단이 아니라 사고처럼
보였다.** 고른 것과 그냥 그렇게 된 것의 차이는 코드가 아니라 **숫자와 기록**에 있다.
(파생 결함 2개 — 메모리가 코퍼스에 비례, 인덱싱·서빙 결합으로 재인덱싱에 서버 정지 필요 —
는 실재하며, 이것이 pgvector 이전의 명분이다. "벡터DB 경험이 필요해서"가 아니라.)

## 16. 코퍼스를 프로필로 분리 — 유출 방지가 아니라 측정 재현성이 먼저였다

**증상**: 지식원 경로가 `.env` 의 로컬 절대경로라 ①다른 PC 에서 clone 해도 인덱싱 불가
②CI 러너에 그 경로가 없어 **회귀 게이트를 돌릴 코퍼스가 없음** ③공개 데모에 비공개 코퍼스를 올릴 수 없음.

**원인**: "무엇을 인덱싱하는가"가 설정 파일에 흩어져 있었고, 그것이 곧 실행 환경에 대한 의존이었다.

**해결**: 코퍼스 프로필(`app/profiles.py`) — (지식원 · 컬렉션 · 평가셋) 을 한 벌로 묶는다.
`demo` 는 **이 저장소 자기 자신**, `private` 은 `.env` 로 지정한 외부 코드베이스.
두 프로필은 같은 chroma 디렉터리 안에서 **컬렉션 이름으로 분리**해 공존한다(전환에 재인덱싱 불필요).

**핵심 결정**: demo 코퍼스를 폴더 walk 가 아니라 **`git ls-files`(추적 파일)** 로 정의했다.
폴더로 잡으면 로컬에만 있는 개인 메모가 섞여 **같은 코드인데 PC·CI 마다 청크 수와 recall 이 달라진다.**
추적 파일 집합은 커밋 해시로 고정되므로 어디서든 동일하다. 유출 방지는 그 결정에 딸려온 부산물이다
(비공개 파일은 애초에 `.gitignore` 대상이므로).

**되밟은 함정**: 공통 제외 목록에 `.claude` 를 넣었다가 private 프로필의 **문서 57개가 0개**가 됐다.
그 프로필의 지식원 루트가 하필 `<repo>/.claude/memory` 였다. 제외 목록은 '가상환경·캐시·산출물'로만
한정하고, 회귀 테스트(`tests/test_profiles.py`)로 박아뒀다.

**교훈**: 재현되지 않는 측정은 측정이 아니다. 회귀 게이트를 세우기 전에
**"어느 머신에서든 같은 코퍼스"** 를 먼저 정의해야 했다. 리팩터링 후 private 재측정으로
recall 93% · 범위밖 5/6 동일을 확인했다(동작 보존 확인 없이 넘어가면 이후 숫자를 못 믿는다).

## 17. 평가표의 행 이름이 잘못된 결론을 만들고 있었다 — 'MMR' 이 아니라 심볼 슬롯

**증상**: demo 코퍼스 기준선을 처음 재보니 `hybrid (RRF)` → `hybrid+MMR` 구간에서
문서 질문 MRR 이 **0.88 → 0.78 로 떨어졌다**. 이름만 보면 "MMR 이 순위를 망친다"가 된다.

**원인**: 그런데 `mmr_lambda=1.0` 이면 **MMR 은 순위를 바꾸지 않는다**(적합도 최대를 순서대로
고르므로 순수 RRF 순위와 같다 — no-op). 즉 그 차이는 MMR 이 만든 게 아니다.
두 행의 진짜 차이는 마지막 행이 `search()` **전체**를 타는 것이었다 —
**심볼 슬롯**(질문 속 ASCII 식별자와 정확매칭되는 코드 청크를 top-k 에 강제로 밀어넣는 장치)과
범위 밖 게이트가 거기 포함돼 있다.

demo 질문에는 `RRF` `MMR` `AST` `ANN` `LangGraph` `API` 같은 영문 토큰이 흔하다.
그래서 **문서를 묻는 질문인데 그 이름을 가진 코드 청크가 앞자리를 차지**했다.

**측정** — 심볼 슬롯은 축에 따라 부호가 반대다:

| 질문 축 | 심볼 슬롯 없음(hybrid RRF) | 있음(운영 파이프라인) |
|---|---:|---:|
| 문서 질문 MRR (demo) | 0.88 | **0.78** ↓ |
| 코드 질문 MRR (private) | 0.44 | **0.53** ↑ |

**해결**: 행 이름을 `hybrid+MMR` → **`운영 파이프라인`** 으로 고치고, 구성 요소를 표 아래
범례로 명시했다(`RRF + 심볼슬롯 + MMR(λ=1.0 → no-op) + 범위밖 게이트`).
recall 은 두 행이 같으므로 **채택 판단이 바뀌지는 않는다** — 바뀌는 건 그 공을 무엇에 돌리느냐다.

**교훈**: 측정값이 맞아도 **라벨이 틀리면 결론이 틀린다.** 이 표는 그대로 포트폴리오·면접에
쓰이므로, "MMR 덕분입니다"라고 말한 순간 코드를 열어본 사람에게 무너진다.
같은 종류의 오귀인을 예전에 한 번 겪었다(#13 의 λ 정정). 그때는 값을, 이번엔 이름을 고쳤다.
그리고 이 양면성은 **의도 라우팅**(질문이 문서를 묻는지 코드를 묻는지 판별해 축을 고르는 일)이
왜 다음 과제인지를 숫자로 보여준다 — 지금은 한 장치가 한쪽 축을 도우면서 다른 축을 깎고 있다.

## 18. 자기 자신을 코퍼스로 삼으면 회귀 게이트가 성립하지 않는다 — 코퍼스를 태그로 고정

**증상**: CI 회귀 게이트를 붙이고 처음 돌린 순간 실패했다.

```
[gate] ✗ 회귀 감지
   - [문서 질문] recall 100% → 92%
   - 새로 실패한 문항: "MMR 다양성 계수를 1.0 으로 정한 근거가 뭐야?"
```

**원인**: 검색 코드는 한 줄도 안 건드렸다. 바뀐 건 **코퍼스**다.
demo 프로필의 지식원은 **이 저장소 자기 자신**이라, 커밋을 하면 코퍼스가 커진다.
baseline 을 만든 뒤 노트 #17 을 쓰고 평가 코드를 추가했더니 285 → 324 청크가 됐다.

하필 새로 실패한 문항이 **MMR 관련 질문**이라는 게 정확한 증거다 —
노트 #17 은 "MMR 이 아니라 심볼 슬롯이었다"는 내용이고, 거기에 MMR 이라는 단어가 잔뜩 들어갔다.
**그 글을 쓴 행위 자체가 그 주제의 검색을 흐트러뜨렸다.**

즉 이 구성에서는 점수가 떨어져도 **"검색이 나빠졌다"와 "문서를 한 편 더 썼다"를 구분할 수 없다.**
자를 만들었는데 잴 때마다 대상이 움직이는 셈이라, 게이트가 잡는 건 회귀가 아니라 잡음이다.

**해결**: 평가용 코퍼스를 **태그로 고정**했다. `eval` 프로필은 `git archive <ref>` 로
`eval-corpus-v1` 시점 파일을 캐시에 풀어 그 위에서 인덱싱한다(`GitSnapshotSource`).
워킹트리가 아무리 바뀌어도 같은 ref 면 같은 코퍼스다. 확인:

| 프로필 | `app/fs_utils.py` 크기 | 최신 코드 포함 |
|---|---:|---|
| demo (워킹트리) | 8,001자 | 있음 |
| eval (고정 스냅샷) | 4,965자 | 없음 |

코퍼스를 갱신하려면 **새 태그를 만들고 baseline 을 다시 생성**한다. 그 둘이 귀찮은 건 의도다 —
코퍼스 변경은 조용히 일어나면 안 되는 사건이다.

**교훈**: 회귀 게이트를 세우기 전에 **"무엇이 고정이고 무엇이 변수인가"** 를 정해야 한다.
노트 #16 에서 "어느 머신에서든 같은 코퍼스"를 만들었지만, 그건 *공간*의 고정이었고
**시간의 고정이 빠져 있었다.** 둘 다 있어야 비교가 성립한다.
그리고 이 결함은 게이트를 실제로 돌려봤기 때문에 **첫 실행에서 바로 드러났다** — 만들어만 두고
초록불을 확인하지 않았다면, 몇 주 뒤 진짜 회귀가 났을 때 "또 코퍼스 바뀌었겠지"로 넘겼을 것이다.

## 19. 문항을 20 → 258개로 늘리자 점수가 무너졌다 — 그리고 무너진 자리가 뜻밖이었다

**배경**: 수기 평가셋 20문항으로 잰 recall@5 는 85% 였다. 그런데 그 20문항은 **내가 냈다.**
내가 아는 것을 물었으니 시스템이 잘 답할 질문에 기울었을 수 있고, 그러면 85% 는
성능이 아니라 출제 경향을 재고 있는 것이다. 그래서 원본 청크에서 LLM 이 질문을 만들게 해
**258문항**으로 늘렸다(`eval/generate.py`).

순환을 피하는 것이 설계의 전부였다: 질문은 **원본 청크**에서 만들고 정답 라벨은 그 청크의
파일 경로를 그대로 쓴다. **검색기를 한 번도 부르지 않는다** — 검색 결과로 라벨을 만들면
"검색기가 찾은 것이 정답"이 되어 점수가 자기 자신을 증명하게 된다.

**결과** (같은 고정 코퍼스, 같은 검색 코드, k=5):

| 평가셋 | 문항 | 전체 recall@5 | 문서 | 코드 | 커밋 |
|---|---:|---:|---:|---:|---:|
| 수기 골든셋 | 20 | **85%** | 92% | 75% | *(문항 없음)* |
| 합성셋 | 258 | **79%** | 82% | 82% | **69%** |

**세 가지가 드러났다.**

1. **6%p 가 출제 경향이었다.** 코드가 아니라 문항이 바뀌었을 뿐인데 점수가 내려갔다.
   85% 는 "내가 낸 문제에서의 85%" 였다.

2. **★수기 셋은 커밋 축을 아예 재고 있지 않았다.** 20문항 중 커밋만으로 답하는 문항이
   **0개**였다(멀티홉의 한 홉으로만 등장). 합성셋이 54문항을 만들어 그 축을 처음 측정했고,
   **69% 로 세 축 중 최약점**이었다. 없는 문항은 낮은 점수를 만들지 않는다 — **아무 점수도
   만들지 않아서 안 보인다.** 평가셋의 구멍은 나쁜 점수가 아니라 침묵으로 나타난다.

3. **코드 축은 오히려 올랐다**(75% → 82%). 수기 코드 문항이 8개뿐이라 표본 오차가 컸다는 뜻이고,
   그 8개로 "코드 질문이 약하다"고 판단했던 근거가 흔들린다. 표본이 작으면 강점도 약점도 못 잰다.

부수 확인: 심볼 슬롯의 코드 축 기여가 182문항 표본에서도 재현됐다(77% → 82%). 노트 #17 의
관찰이 8문항 우연이 아니었다는 뜻이다.

**남은 한계 — 이 79% 도 아직 그대로 쓸 수 없다.** 합성 라벨은 "그 청크의 파일"일 뿐이라,
같은 답이 다른 파일에도 있으면 **검색기가 옳은 파일을 찾고도 miss 로 채점된다**(거짓 오답).
그래서 49문항 표본을 사람이 직접 검수해 **합성 라벨 vs 수동 라벨 불일치율**을 재고,
그 값을 79% 의 오차 막대로 붙인다(`eval/verify.py`). 검수 워크시트에는 **검색기 출력을
싣지 않는다** — 그걸 보고 판정하면 검수가 검색기를 정당화하는 절차로 변한다.

**교훈**: 평가셋을 늘리는 일은 "점수를 정확하게 만드는 것"이 아니라 **"무엇을 재고 있지
않았는지 드러내는 것"**이다. 79% 는 85% 보다 나쁜 숫자가 아니라 **더 많은 것을 재고 있는 숫자**다.

## 20. 라벨을 보정했더니 보정값이 판정기에 따라 84%↔94% 로 흔들렸다

**배경**: 합성 평가셋의 정답은 "질문을 만들어 낸 청크의 파일" 하나뿐이라, 같은 답이 다른
파일에도 있으면 **검색기가 옳게 찾고도 miss** 가 된다(거짓 오답). 이걸 세지 않으면 79.5% 라는
값을 믿을 수 없다.

**사람이 못 하는 검수였다.** 검수자가 "다른 파일에도 답이 있나"를 판정하려면 저장소 전체를
알아야 한다. 그건 사람보다 기계가 낫다. 그래서 역할을 갈랐다:

    사람 — "이 조각이 이 질문에 답하나?"   (화면의 조각만 읽으면 됨. 도메인 지식 불필요)
    기계 — "다른 파일에도 답이 있나?"      (전수 확인 — `eval/audit_misses.py`)

**측정**: miss 53건 중 무작위 20건을 **생성기와 다른 모델**로 감사.

| | 값 |
|---|---:|
| 원래 recall@5 | 79.5% |
| 판정한 miss | 20/53 (표본) |
| 그중 거짓 오답 | **14건 = miss 의 70%** |
| 거짓 오답률(전체 외삽) | 14.4% |
| **보정 recall@5** | **93.8%** (추정) |

실제로 잡힌 사례를 보면 판정이 타당하다. 예: *"Gemini 응답에 텍스트가 아닌 요소가 섞이면
어떻게 처리돼?"* → 라벨은 `tests/test_text_normalize.py` 하나였는데, `app/rag.py`(구현),
`docs/engineering-notes.md`(#1), 해당 커밋에도 답이 있다. 검색기는 옳게 찾았고 라벨이 좁았다.

**★ 그런데 진짜 결과는 이것이다.** 같은 감사를 다른 판정 모델로 돌렸을 때:

| 감사 모델 | 판정한 miss | 거짓 오답 비율 | 보정 recall(환산) |
|---|---:|---:|---:|
| `gemini-3-flash-preview` | 20건 | **70%** | ~93.8% |
| `gemini-3.5-flash` | 17건 | **23.5%** | ~84.3% |

**판정기를 바꿨을 뿐인데 보정값이 10%p 벌어졌다.** (표본이 서로 달라 엄밀한 통제 비교는
아니지만, 3배 차이를 표본 우연으로만 설명하기는 어렵다. 동일 표본 통제 비교는 다음 과제.)

**결론 — 보정 recall 을 단일 숫자로 인용하지 않는다.** 79.5%(하한, 라벨이 좁음)와
93.8%(상한, 판정기가 관대할 수 있음) **사이의 구간**으로 보고한다. 어느 한쪽만 적으면
숫자를 유리하게 고른 것이 된다.

**부수 발견 — 무료 티어 쿼터는 모델마다 다르고, '분당'이 아닌 것도 있다.**
`gemini-3.5-flash` 는 `GenerateRequestsPerDayPerProjectPerModel-FreeTier` **일 20건**이라
53건 전수 감사가 애초에 불가능했다. 노트 #12 에서 분당 제한을 설계에 반영했는데, 그것만으론
부족했다. 그래서 감사기를 **표본 추출 + 중단 안전**(쿼터가 끊겨도 거기까지를 표본으로 집계)으로
바꿨다. 평가 도구는 **중간에 죽어도 결과를 남겨야** 한다 — 그러지 않으면 쿼터를 태우고 아무것도
못 건진다.

**교훈**: 편향을 보정하는 장치를 만들면 **그 장치의 편향**이 새로 생긴다. 보정 절차는 구조상
recall 을 올리는 방향으로만 작동하므로, 원래 값과 함께 적지 않으면 점수를 올리는 도구가 된다.

## 21. self-judge 편향을 재려다 더 나쁜 걸 찾았다 — 판정기들이 평균만 같고 합의는 0

**배경**: groundedness 0.962 의 문제는 값이 아니라 출처였다. 생성한 모델이 자기 답을 채점했으니
(self-enhancement bias) 얼마나 후한지 모르면 쓸 수 없다. 그래서 판정기를 갈아끼워 편차를 재기로 했다.

**먼저, 기존 방식은 통제가 아니었다.** `faithfulness.py --judge-model X` 를 두 번 돌리면
판정기는 바뀌지만 **답변도 매번 새로 생성된다.** 그러면 점수 차이가 판정기 탓인지 답변 탓인지
나눌 수 없다. 절차를 잘랐다(`eval/judge_panel.py`):

    freeze  — 답변을 한 번 만들어 (질문, 근거, 답변) 을 고정한다
    judge   — 그 고정된 입력만 판정기에 건다
    compare — 쌍별로 편차를 낸다

동결본을 쓰는 한, 몇 달 뒤 다른 모델을 붙여도 같은 비교가 성립한다.

**측정** — 생성기 `gemini-3.1-flash-lite` 의 동일 답변 16문항(범위밖 1 포함), 판정기만 교체:

| 판정기 | 종류 | 채점 | 평균 | 환각 지적 |
|---|---|---:|---:|---:|
| `gemini-3.1-flash-lite` | **self** | 16 | 0.979 | 6% |
| `gemini-3.5-flash-lite` | cross | 16 | 1.000 | 0% |
| RAGAS `Faithfulness` (같은 모델, 다른 도구) | cross | 15 | 0.986 | 13% |
| `gemini-3-flash-preview` | cross | 4 | 0.950 | 25% |
| `gemini-3.5-flash` | cross | 4 | 1.000 | 0% |

**★ 가설이 틀렸다. self-judge 가 가장 후하지 않았다.** self(0.979)는 cross-lite(1.000)와
RAGAS(0.986)보다 **낮다.** 이 표본에서 self-enhancement bias 는 관측되지 않았고, 오히려
self 판정기가 유일하게 잡아낸 감점 문항이 있다.

**그런데 진짜 결과는 평균이 아니라 합의다.** 감점한 문항을 나열해 보면:

| 판정기 | 감점한 문항 |
|---|---|
| self `3.1-flash-lite` | q03 (평가 하네스 타임아웃 원인) |
| RAGAS | q01 (self-judge 편향 처리), q14 (판정 프롬프트 위치) |
| `3-flash-preview` | q02 (git 추적 파일 코퍼스) |
| `3.5-flash-lite`, `3.5-flash` | 없음 |

**한 문항도 겹치지 않는다.** Cohen's κ 로 확인하면 계산 가능한 쌍이 전부 **음수**다
(RAGAS↔self **-0.098**, `3-flash-preview`↔self **-0.333**) — 우연히 맞추는 것보다도 못하다.
나머지 쌍은 한쪽이 전 문항 만점이라 κ 가 아예 **정의되지 않는다**.

    평균 차이   0.9%p ~ 2.1%p   → "판정기가 견고하다"고 읽고 싶어진다
    Cohen's κ   ≈ -0.1 ~ -0.33  → 어느 답이 환각인지에 대한 합의는 0

**평균 일치는 합의가 아니라 천장 효과였다.** 답변이 대부분 만점이라 평균이 자동으로 모인다.
평균만 보고 "판정기를 바꿔도 값이 같으니 믿을 만하다"고 결론냈으면 정반대로 틀렸을 것이다.

**노트 #20 과 나란히 놓으면 규칙이 보인다.** 같은 판정기 교체가 라벨 감사에서는 10%p 를
벌렸는데(70% ↔ 23.5%) 여기서는 2%p 안에 들어왔다. 차이는 **과제 난도**다. 라벨 감사는
판정이 어려운 문항(miss)만 골라 걸었고, groundedness 는 대부분 쉬운 문항이라 천장에 붙었다.
→ **판정기 편차는 판정기의 속성이 아니라 과제의 속성이다.** 쉬운 평가셋에 판정기를 여러 개
걸어 놓고 "일치한다"고 쓰는 건 아무것도 증명하지 않는다.

**그래서 결론이 바뀐다.** groundedness 0.979 를 못 믿는 이유는 이제 "self-judge 라서"가
아니다. **평가셋이 쉬워서 어떤 판정기도 변별하지 못하기 때문**이다. 다음 과제는 판정기를
더 붙이는 게 아니라 **환각을 유도하는 어려운 문항을 확보하는 것**이다. 지금 골든셋으로는
판정기를 몇 개 더 붙여도 전부 1.00 이 나온다.

**무료 티어가 실험 설계를 규정했다.** 큰 모델은 하루 4~5건에서 끊긴다
(`gemini-3.5-flash`·`gemini-3-flash-preview` 둘 다 4건에서 429, 재시도 지연 671초 = 일 단위 쿼터).
전 문항 교차 판정이 가능한 건 사실상 `-lite` 계열뿐이고, 그 계열은 전부 만점을 준다.
그래서 도구에 두 가지를 박았다.

- **중단 안전** — 쿼터가 끊겨도 거기까지를 보존하고, `compare` 는 **쌍별 교집합**으로 본다.
  전체 교집합을 쓰면 한 판정기가 못 채점한 문항 때문에 무관한 쌍의 표본까지 깎인다.
- **표본 하한** — n<8 인 쌍은 부트스트랩 구간이 0 을 안 걸쳐도 **유의라고 쓰지 않는다.**
  n=4 에서 구간이 0 을 비켜 가는 건 통계가 아니라 우연이다.

**계산에서 조심한 것 둘.**
`Cohen's κ` 는 한쪽이 전 문항 같은 판정이면 상대가 뭘 하든 항상 0 이 나온다(κ 역설).
그 0 을 "우연 수준 일치"로 읽으면 틀리므로 **정의되지 않음(n/a)** 으로 남긴다 — 판정기가 모든
답에 1.00 을 주는 일은 실제로 흔해서 꼭 필요한 구분이었다. Spearman ρ 도 같은 이유로 n/a 를 낸다.

**부수 발견 — 이름 충돌로 RAGAS 대조가 한 번도 돌지 않고 있었다.**
`eval/ragas_score.py` 를 직접 실행하면 `eval/` 이 `sys.path` 맨 앞에 오고, 우리 `eval/datasets.py`
가 HuggingFace `datasets` 패키지를 가린다. `ragas.utils` 의 `from datasets import Dataset` 이
우리 파일을 집어 격리 환경에 없는 `app` 을 임포트하며 죽었다. 스크립트 디렉터리를 경로에서
빼서 고쳤다. **표준 라이브러리·유명 패키지와 겹치는 모듈명은 패키지 안이라도 안전하지 않다.**

**교훈**: 두 측정치가 같다는 것은 두 측정기가 일치한다는 뜻이 아니다. 평균이 모이는 이유가
합의인지 천장인지 먼저 확인해야 하고, 그걸 보려면 평균이 아니라 **문항 단위 일치도**를 봐야 한다.
